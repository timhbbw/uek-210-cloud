# 3.5 Python-Container, docker scout und Volumes

Alle Befehle werden im Repo-Root (`uek-210-cloud/`) in PowerShell ausgeführt, da die Dockerfiles mit Pfaden relativ zum Repo-Root arbeiten.

## 1. Vorbereitung

- `app/file-reader/data.txt` erstellt (Inhalt beim Build: `Version 1 (beim Build ins Image kopiert)`).

## 2. + 3. Python-Webserver bauen und starten

Dockerfile: `dockerfiles/block3/Dockerfile.task.3.5.web`

```powershell
docker build -f dockerfiles/block3/Dockerfile.task.3.5.web -t python-web:v1 .
docker run -d --name python-web -p 8080:8080 python-web:v1
```

- Test: http://localhost:8080?name=Tim → `Hello, Tim!`
- Ohne Parameter: http://localhost:8080 → `Hello, World!`
- Wichtig: Nur ein `FROM python:3.11-alpine`. Ein zweites `FROM nginx:alpine` würde das Python-Image ersetzen und Flask würde nie laufen.

## 4. Sicherheitscheck mit docker scout

Voraussetzung: Mit Docker-ID angemeldet sein (`docker login`), sonst verweigert docker scout den Dienst.

```powershell
# Übersicht
docker scout quickview local://python-web:v1
docker scout quickview python:alpine

# Detaillierte CVE-Liste
docker scout cves local://python-web:v1
docker scout cves python:alpine

# Direkter Vergleich
docker scout compare local://python-web:v1 --to python:alpine

# Zum Vergleich: volles Debian-Image
docker scout quickview python:3.11
```

- Resultate:
    - `python-web:v1` (python:3.11-alpine + Flask): _C / H / M / L eintragen_
    - `python:alpine`: _C / H / M / L eintragen_
    - `python:3.11` (Debian): _C / H / M / L eintragen_
- Erkenntnisse:
    - Alpine-Images sind klein (musl, BusyBox, wenige Pakete), dadurch kleine Angriffsfläche und wenige CVEs.
    - Das volle `python:3.11` (Debian) enthält hunderte OS-Pakete, entsprechend deutlich mehr CVEs.
    - `python:alpine` (latest) hat eine neuere Python-Version und neuere Pakete als `3.11-alpine`, deshalb meist noch weniger CVEs.
    - Unser Image bringt zusätzlich Flask und seine Abhängigkeiten (Werkzeug, Jinja2, ...) mit, die eigene CVEs haben können.
    - Fazit: Kleine Basis-Images wählen und Images regelmässig neu bauen, damit Sicherheits-Patches übernommen werden.

## 5. + 6. File-Reader: Build vs. Laufzeit

Dockerfile: `dockerfiles/block3/Dockerfile.task.3.5.reader` (kopiert `data.txt` per `COPY` nach `/data/data.txt`)

```powershell
docker build -f dockerfiles/block3/Dockerfile.task.3.5.reader -t file-reader:v1 .
docker run -d --name file-reader -p 8081:8080 file-reader:v1
```

- http://localhost:8081 → `Inhalt der Datei: Version 1 (beim Build ins Image kopiert)`
- `data.txt` auf dem Host geändert auf `Version 2 (auf dem Host geaendert)`.
- http://localhost:8081 zeigt weiterhin `Version 1`, ebenso `docker exec file-reader cat /data/data.txt`.

## 7. Volumes nutzen (Bind-Mount)

```powershell
docker rm -f file-reader
docker run -d --name file-reader -p 8081:8080 -v "${PWD}/Block3/3.5/app/file-reader/data.txt:/data/data.txt" file-reader:v1
```

- http://localhost:8081 zeigt sofort den aktuellen Host-Inhalt (`Version 2`).
- `data.txt` auf dem Host geändert auf `Version 3 (live via Bind-Mount, ohne Rebuild)`, Browser neu laden: sofort sichtbar, kein neuer Build nötig.
- Kontrolle: `docker inspect file-reader --format "{{range .Mounts}}{{.Type}}: {{.Source}} -> {{.Destination}}{{end}}"`
- Tipp: Manche Editoren speichern, indem sie die Datei ersetzen statt überschreiben. Dann "verliert" ein Einzeldatei-Mount die Verbindung. Robuster ist es, den ganzen Ordner zu mounten (`-v "${PWD}/Block3/3.5/app/file-reader:/data"`).

## Fehlersuche: Warum sind Änderungen ohne Volume-Mount unsichtbar?

- `COPY` wird nur beim `docker build` ausgeführt. Der Inhalt von `data.txt` wird dabei in einen schreibgeschützten Image-Layer "gebrannt" (Snapshot zum Build-Zeitpunkt).
- Der Container liest `/data/data.txt` aus diesem Layer, nicht vom Host. Zwischen Host-Datei und Container besteht keine Verbindung.
- Eine Änderung am Host wird erst nach einem neuen `docker build` und einem neuen Container sichtbar.
- Ein Bind-Mount (`-v`) legt die Host-Datei zur Laufzeit über den Pfad im Container ("überlagert" die Datei aus dem Image). Der Container liest dann direkt die Host-Datei.
- Faustregel: Code und Abhängigkeiten gehören ins Image (Build-Zeit), veränderliche Daten und Konfiguration in Volumes (Laufzeit).
