Beantworten Sie folgende Fragen in der Gruppe und notieren Sie Ihre Antworten stichwortartig:

- Was ist Container-Technologie bzw. Container-Virtualisierung?
    - Container-Technologie (bspw. Docker) bietet die Möglichkeit, Applikationen inklusive aller Abhängigkeiten (Libraries, Laufzeitumgebung, Konfiguration) in einer isolierten Einheit zu verpacken und zu betreiben.
    - Mehrere Container teilen sich den Kernel des Host-Betriebssystems, sind aber voneinander isoliert (Linux Namespaces und cgroups).
    - Container sind deshalb deutlich leichtgewichtiger als virtuelle Server.
- Was sind die Vor- und Nachteile von Containern gegenüber virtuellen Servern (VMs)?
    - Vorteile
        - Starten in Sekunden, da kein komplettes Betriebssystem gebootet werden muss.
        - Geringerer Ressourcenverbrauch, dadurch höhere Dichte pro Host.
        - Sehr portabel und überall identisch lauffähig (Entwicklung = Test = Produktion).
        - Gut geeignet für Microservices und CI/CD.
    - Nachteile
        - Schwächere Isolation, da der Kernel geteilt wird.
        - Container sind an den Host-Kernel gebunden (Linux-Container brauchen einen Linux-Kernel).
        - Persistente Daten und Netzwerk sind aufwändiger zu handhaben.
        - Bei vielen Containern wird eine Orchestrierung (z.B. Kubernetes) nötig, was die Komplexität erhöht.

- Wie unterscheiden sich VM und Container hinsichtlich Bereitstellung, Speicherbedarf, Portabilität, Effizienz und OS-Kernel?
    - Bereitstellung
        - VM: Dauert Minuten, da ein ganzes Betriebssystem installiert und gebootet wird.
        - Container: Dauert Sekunden, da nur das Image gestartet wird.
    - Speicherbedarf
        - VM: Gross (GB), da jede VM ein komplettes Gast-Betriebssystem enthält.
        - Container: Klein (MB), da nur Applikation und Abhängigkeiten enthalten sind.
    - Portabilität
        - VM: Eingeschränkt, grosse Images und teilweise abhängig vom Hypervisor.
        - Container: Sehr hoch, läuft überall, wo eine Container Runtime vorhanden ist.
    - Effizienz
        - VM: Overhead durch Hypervisor und Gast-Betriebssystem.
        - Container: Nahe an nativer Performance, kaum Overhead.
    - OS-Kernel
        - VM: Hat einen eigenen Kernel pro VM.
        - Container: Teilt sich den Kernel des Hosts.
- Können virtuelle Server immer durch Container ersetzt werden? Begründen Sie.
    - Nein.
    - Applikationen, die ein anderes Betriebssystem bzw. einen anderen Kernel benötigen (z.B. Windows-Applikation auf einem Linux-Host).
    - Legacy-Software, die nicht containerisiert werden kann.
    - Hohe Isolationsanforderungen (Mandantentrennung, Compliance, Sicherheit), da Container den Kernel teilen.
    - Applikationen mit Kernel-Anpassungen oder grafischer Oberfläche.
    - In der Praxis ergänzen sich beide: Container laufen häufig innerhalb von VMs.
- Können Sie die Begriffe Container, Image und Registry erläutern?
    - Image
        - Schreibgeschützte Vorlage, bestehend aus mehreren Schichten (Layers).
        - Enthält Applikation, Abhängigkeiten und Konfiguration.
    - Container
        - Laufende Instanz eines Images.
        - Aus einem Image können beliebig viele Container gestartet werden.
    - Registry
        - Ablage- und Verteilungsort für Images, z.B. Docker Hub oder GitHub Container Registry.
        - Kann öffentlich oder privat sein, Versionen werden über Tags verwaltet.
- Dockerfile: Welche Rolle spielt das Dockerfile im Build-Prozess und wie führt es Applikationscode, Basis-Betriebssystem und Laufzeitumgebung zusammen?
    - Das Dockerfile ist eine Textdatei mit der Bauanleitung für ein Image. Daraus entsteht mit `docker build` Schicht für Schicht das Image.
    - `FROM` legt das Basis-Image fest (Basis-Betriebssystem und Laufzeitumgebung).
    - `COPY` bringt den Applikationscode ins Image.
    - `RUN` installiert Abhängigkeiten bzw. baut die Applikation.
    - `ENV` / `EXPOSE` definieren Umgebungsvariablen und Ports.
    - `CMD` / `ENTRYPOINT` definieren, was beim Start des Containers ausgeführt wird.
    - Dadurch ist der Build reproduzierbar und versionierbar (Infrastructure as Code).

- Weshalb werden laufende Container in der Praxis als unveränderbar (immutable) betrachtet?
    - Änderungen im laufenden Container gehen beim Neustart verloren (die beschreibbare Schicht ist flüchtig).
    - Änderungen werden deshalb im Image bzw. Dockerfile gemacht, ein neues Image gebaut und der alte Container ersetzt.
    - Vorteile: Reproduzierbarkeit, konsistente Umgebungen, kein Configuration Drift, einfaches Rollback und einfaches Skalieren.
    - Persistente Daten gehören in Volumes oder externe Speicher.
- Was ist der Unterschied zwischen Self-Managed und Fully Managed (Cloud-Services)?
    - Self-Managed
        - Der Kunde installiert, betreibt, patcht und skaliert die Lösung selbst (z.B. eigener Kubernetes-Cluster oder eigene Datenbank auf einer VM).
        - Volle Kontrolle, aber hoher Aufwand und viel Know-how nötig.
    - Fully Managed
        - Der Provider übernimmt Betrieb, Updates, Backups, Skalierung und Hochverfügbarkeit (z.B. Amazon EKS, Azure Container Apps, Google Cloud Run, Amazon RDS).
        - Weniger Aufwand für den Kunden, dafür weniger Kontrolle, meist höhere Kosten und mehr Abhängigkeit vom Provider (Vendor Lock-in).
    - Auch hier gilt Shared Responsibility: Je mehr der Provider managt, desto kleiner ist der Verantwortungsbereich des Kunden.
