#### Warum braucht man Container-Orchestrierung?
- Sobald man viele Container auf mehreren Hosts betreibt, ist manuelles Starten, Überwachen und Skalieren nicht mehr praktikabel.
- Die Orchestrierung automatisiert:
    - Deployment und Updates der Container
    - Skalierung (hoch und runter, je nach Last)
    - Selbstheilung (ausgefallene Container werden automatisch neu gestartet)
    - Load Balancing und Service Discovery
    - Verteilung der Container auf die verfügbaren Hosts
    - Verwaltung von Konfiguration und Secrets

#### Wie funktioniert Container-Orchestrierung?
- Der gewünschte Zustand (Desired State) wird deklarativ beschrieben, z.B. in einer YAML-Datei ("3 Replikas von Image X").
- Der Orchestrator vergleicht laufend den Ist-Zustand mit dem Soll-Zustand und korrigiert Abweichungen automatisch (Control Loop).
- Aufbau am Beispiel Kubernetes:
    - Control Plane: API-Server, Scheduler, Controller Manager und etcd (Speicher für den Cluster-Zustand).
    - Worker Nodes: Hier laufen die Container (Pods), verwaltet durch den kubelet und die Container Runtime.
    - Der Scheduler verteilt die Pods anhand der verfügbaren Ressourcen auf die Nodes.
    - Services und Ingress verteilen den Netzwerkverkehr auf die Pods (Load Balancing).
    - Fällt ein Container oder ein Node aus, werden die Pods automatisch neu gestartet bzw. auf andere Nodes verschoben.

#### Welche Container-Orchestrierung Technologien kennen Sie?
- Kubernetes (k8s / k3s)
- Docker Compose (nur für einen einzelnen Host, einfache Definition mehrerer Container)
- Docker Swarm
- OpenShift
- HashiCorp Nomad
- Amazon ECS
- Fully Managed Varianten: Amazon EKS, Azure AKS, Google GKE

#### Was versteht man unter horizontaler Skalierung im Kontext von Cloud-Anwendungen?
- Bei der horizontalen Skalierung (Scale Out) werden zusätzliche Instanzen (Server, VMs oder Container) hinzugefügt. Ein Load Balancer verteilt die Last auf alle Instanzen.
- Gegensatz: Bei der vertikalen Skalierung (Scale Up) wird einem bestehenden Server mehr Leistung (CPU, RAM) zugeteilt.
- Vorteile:
    - Kaum Grenzen durch die Hardware eines einzelnen Servers.
    - Höhere Ausfallsicherheit, da mehrere Instanzen laufen.
    - Lässt sich automatisieren (Autoscaling).
- Nachteile:
    - Die Anwendung sollte möglichst stateless sein.
    - Höhere Komplexität (Load Balancing, Datenhaltung).

#### Was gibt es für Deployment Strategien?
- Recreate/Basic
    - Hat Downtime, alles wird heruntergefahren, aktualisiert und anschliessend wieder hochgefahren.
    - Einfach und günstig, aber nicht für produktive Systeme mit Verfügbarkeitsanspruch geeignet.
- Rolling Update
    - Instanzen werden eine nach der anderen (oder in kleinen Gruppen) aktualisiert => Keine Downtime.
    - Während des Updates laufen alte und neue Version parallel, diese müssen also kompatibel sein.
    - Rollback ist langsamer, da wieder schrittweise zurückgerollt wird.
- Blue / Green
    - Es gibt zwei identische Umgebungen: Blue (aktuelle Version) und Green (neue Version).
    - Die neue Version wird auf Green deployt und getestet, danach wird der gesamte Traffic auf einmal umgeschaltet => Keine Downtime.
    - Rollback ist sehr schnell, durch Zurückschalten auf Blue.
    - Nachteil: Doppelter Ressourcenbedarf während des Deployments.
- Canary
    - Die neue Version erhält zuerst nur einen kleinen Teil des Traffics (z.B. 5%), der Rest bleibt auf der alten Version.
    - Läuft die neue Version stabil (Metriken, Fehlerrate), wird der Anteil schrittweise erhöht.
    - Fehler betreffen nur wenige Nutzer, dafür ist der Aufwand für Überwachung und Traffic-Steuerung höher.
